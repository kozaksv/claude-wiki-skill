# Wiki Skill

**Версія скіла: 4.12.1 · Типовий install ref: `master` · Схема вікі: `4.0`**

Спільна LLM-вікі проєкту для **Claude Code, Codex, agy CLI, Qwen Code та ChatGPT з GitHub**.
Агент спершу читає вікі, відповідає з посиланнями на прочитані сторінки й зберігає
нові рішення назад. Знання живуть у вашому Git-репозиторії, а не в пам’яті окремого чату.

## Як це працює

- **Вікі** — Markdown у `docs/wiki/` (або там, куди вказує розділ `## Wiki` /
  `## Вікі`): `concepts/`, `entities/`, `transcripts/`, `index.md`, `schema.md`.
- **Інструкції проєкту — один файл `AGENTS.md`.** Його читають усі підтримувані агенти;
  окремі `CLAUDE.md`, `GEMINI.md`, `QWEN.md` скіл більше не створює.
- **Один скіл на всіх агентів:** справжній клон лежить у `~/claude-wiki-skill`,
  інші шляхи — посилання на нього.
- **Session-хуки Claude Code та Qwen** коротко нагадують шлях до вікі на старті
  сесії й тихо ведуть локальну телеметрію читання сторінок.

## Встановлення

Потрібні **Git і Bash**; для session-хуків — **Python 3**; `curl` — щоб завантажити
інсталятор. Claude Code встановлювати не обов’язково.

```bash
curl -fsSL https://raw.githubusercontent.com/kozaksv/claude-wiki-skill/master/install.sh | bash
```

Інсталятор написаний так, що обірване завантаження нічого не виконає.

Інсталятор створює один клон і посилання на нього для кожного агента:

<!-- harness-exports:start -->
| Harness | Global wiki entrypoint | Kind |
|---|---|---|
| claude | `~/.claude/skills/wiki` | canonical |
| codex | `~/.agents/skills/wiki` | export |
| agy | `~/.gemini/config/skills/wiki` | export |
| qwen | `~/.qwen/skills/wiki` | export |
<!-- harness-exports:end -->

Окремо ставиться необов’язковий `doc-extract` для PDF/DOCX (`ingest-binary`).
Без нього працюють усі операції з Markdown. Системні залежності:

```bash
bash "$HOME/.claude/skills/doc-extract/bin/install-deps.sh"
bash "$HOME/.claude/skills/doc-extract/bin/doctor.sh"
```

**Gemini CLI не підтримується;** з Google-агентів — лише agy CLI. Під час оновлення
інсталятор спершу створює посилання для agy, а потім прибирає лише власні старі
посилання `~/.gemini/skills/wiki` і `~/.gemini/skills/doc-extract`. Налаштування,
облікові дані й чужі скіли в `~/.gemini` не чіпаються.

## Оновлення

Найпростіше — попросіть агента: **«онови wiki-скіл»**. Або з каталогу Git-проєкту,
де ви користуєтеся вікі:

```bash
curl -fsSL https://raw.githubusercontent.com/kozaksv/claude-wiki-skill/master/install.sh | bash
```

Оновлюйте саме так, а не лише `git pull`: Git оновлює файли, але не мігрує
реєстрації хуків і посилання агентів.

Оновлення:

1. оновлює клон без force reset і без перезапису локальних змін;
2. звіряє посилання агентів із реєстром (`lib/harnesses.sh`);
3. оновлює глобальні хуки й прибирає лише однозначно власні старі реєстрації у
   вибраних проєктах;
4. перечитує налаштування й звітує про результат.

Поточний проєкт підхоплюється автоматично. Кілька проєктів або worktree передайте
явно — інсталятор не обходить весь HOME:

```bash
curl -fsSL https://raw.githubusercontent.com/kozaksv/claude-wiki-skill/master/install.sh | bash -s -- master --project /path/a --project /path/b
```

| Результат | Що означає |
|---|---|
| `wiki hooks: verified` | Статична перевірка налаштувань пройшла. Це ще не доказ, що хук спрацював у сесії. |
| `incomplete` / код `3` | Скіл оновлено, але хуки потребують уваги — причина надрукована вище. |
| код `2` у `--repair-exports` | Частину посилань не створено через конфлікт; чужі файли збережено. |

**Фіксована версія та відкат.** Аргумент інсталятора — Git ref: `master`, тег
(наприклад `v4.12.0`) або SHA. Збережіть `git -C ~/claude-wiki-skill rev-parse HEAD`
перед оновленням і передайте цей SHA, щоб повернутися. Відкат скіла не відновлює
старі налаштування автоматично — для цього є копії `.bak-wiki-hooks-*`.

`version` у `SKILL.md` — версія поведінки скіла; `wiki_version` у `schema.md` —
формат даних вікі. Він лишається `4.0`: переписувати вікі через оновлення не потрібно.

Оновіть скіл **на всіх машинах**: старі версії можуть знову запропонувати
створити `CLAUDE.md`, `GEMINI.md`, `QWEN.md`.

## Використання

Відкрийте Git-проєкт в агенті й скажіть **«створи вікі»**. Наявна вікі повторно не
створюється. В порожньому проєкті з’явиться `AGENTS.md` з коротким розділом `## Wiki`;
якщо в проєкті вже є старі instruction-файли, скіл їх не чіпає й запропонує
консолідацію ([нижче](#перехід-на-agentsmd)).

| Намір | Приклад |
|---|---|
| Запит із джерелами | «Як у цьому проєкті працює авторизація?» |
| Зберегти знання | «Додай це рішення у вікі» |
| Перевірити стан | `wiki status` або `wiki doctor` |
| Перевірити зміст | `wiki lint`, `wiki lint швидко`, `wiki lint concepts/auth/` |
| Перебудувати матеріал | «Розділи цю сторінку на поточні правила й історію» |
| Захистити важливе | `wiki protect concepts/recovery.md` |
| Прибрати зайве | `wiki cleanup` |
| Звести старі інструкції | «Перенеси правила з CLAUDE.md в AGENTS.md» |

Читання нічого не змінює: запит не запускає міграцій, ремонту чи комітів.
Якщо в одній теці два файли вказують на **різні** вікі, скіл читає за правилами
вибору, але не пише в жодну, доки ви не вирішите конфлікт. Окремі вікі кореня
й вкладеного компонента — нормальний сценарій.

## Перехід на AGENTS.md

Claude Code читає `AGENTS.md`, лише коли поруч чи вище **немає** `CLAUDE.md`,
`.claude/CLAUDE.md` або `CLAUDE.local.md`. Codex і agy, навпаки, не бачать правил,
що лежать лише в `CLAUDE.md`. Тому старі файли краще звести в один `AGENTS.md`.

Скіл пропонує це один раз — після оновлення, `wiki init` на наявній вікі або
обслуговування вікі. Можна відкласти: інші операції не блокуються. Вручну:

```bash
M="$HOME/.claude/skills/wiki/scripts/migrate.py"
python3 "$M" plan --project "$PWD"     # друкує шлях до плану й що в ньому
python3 "$M" check --plan <plan.json>  # після того як агент переглянув рішення
python3 "$M" apply --plan <plan.json> --write
python3 "$M" commit --plan <plan.json>
```

- **Що робиться автоматично:** однакові копії, файли-заглушки, які колись створив
  скіл, дублікати розділів, рядки-перенаправлення на кшталт `@CLAUDE.md`.
- **Що переглядає агент:** розділи, які є лише в одному файлі, і розділи з однаковою
  назвою, але різним змістом. Рішення фіксуються командою `migrate.py approve`.
- **Що блокує `check`:** загублений фрагмент або правило зі словами
  MUST/NEVER/ЗАБОРОНЕНО/ОБОВ’ЯЗКОВО; зміна вибраної вікі після міграції; посилання
  `@file` на видалений файл; файл понад 24 000 байт (ліміт agy) або понад 32 KiB
  інструкцій на шляху від кореня до теки (ліміт Codex).
- **Безпека:** план, стан і резервні копії зберігаються в `.git/wiki-migration/`, а не в
  робочому дереві. Видаляються лише перелічені файли; чужі незакомічені зміни не
  чіпаються; коміт — один і лише з файлів міграції. Відкат:
  `migrate.py rollback --plan <plan.json> --write` (після коміту — з `--revert`).
- **Необов’язкове скорочення тексту** через `wiki lint` — окремий крок, який можна
  пропустити; критичні правила без вашого рішення не скорочуються.

**Приватні правила `CLAUDE.local.md`** переносяться в `.claude/rules/`, який Git
ігнорує локально (`.git/info/exclude`). Тоді Claude читає і їх, і `AGENTS.md`.
Скіл робить усі кроки сам, а ви двічі підтверджуєте в новій сесії, що правила
завантажились (`/context`, потім `/context` і `/memory`):

```bash
python3 "$M" private prepare --source CLAUDE.local.md --write
python3 "$M" private confirm --source CLAUDE.local.md --checkpoint 1
python3 "$M" private switch  --source CLAUDE.local.md --write
python3 "$M" private confirm --source CLAUDE.local.md --checkpoint 2
```

Глобальні налаштування Claude не змінюються. Подробиці —
[`references/instructions-migration.md`](references/instructions-migration.md).

## ChatGPT з GitHub

Встановіть **Wiki** як особистий скіл і підключіть GitHub:
[покрокова інструкція](docs/chatgpt.md). Пакет —
[`skills/wiki-github`](skills/wiki-github/SKILL.md).

Підтримуються **прямий коміт у `master`/`main` без PR** і **pull request**,
наприклад: «Додай рішення у вікі й закоміть у master без PR». Скіл перевіряє
актуальний commit, права запису та конфлікти; force push не використовує.
Старі instruction-файли віддалено видаляються лише після реального запуску
вбудованого валідатора, інакше — тільки за вашим окремим рішенням.

## Перевірка та відновлення

```bash
bash "$HOME/.claude/skills/wiki/hooks/doctor.sh" --project "$PWD"
```

Doctor нічого не змінює. Він показує стан хуків, вибрану вікі, файли, через які
Claude не читає `AGENTS.md`, і посилання агентів. `wiki doctor` в агенті додатково
перевіряє саму вікі.

| Що полагодити | Команда |
|---|---|
| Реєстрацію хуків | `bash "$HOME/.claude/skills/wiki/hooks/install-hooks.sh" --verify --project "$PWD"` |
| Посилання для Codex, agy, Qwen | `bash "$HOME/.claude/skills/wiki/install.sh" --repair-exports` |

> Ручний запуск `session-start.sh` — **не** перевірка без змін: він оновлює
> `.usage.json` і «витрачає» одноразові нагадування. Для діагностики — `doctor.sh`.

**Як працюють session-хуки:**

| Подія | Поведінка |
|---|---|
| `startup` | Короткий шлях до індексу та одноразові нагадування (lint за зміною вмісту, недоступна телеметрія). |
| `clear`, `compact` | Лише короткий шлях до вікі. |
| `resume` | Не використовується. |
| `PostToolUse` | Тихо оновлює локальну `.usage.json`. |

Хук не вставляє вміст індексу й не означає, що індекс прочитано: агент читає його
сам. Старий `post_tool_use_at` ≠ «вікі не читають»: телеметрія бачить лише файлові
інструменти, а читання через `cat`/`sed` у Bash — ні.

Інсталятор працює лише зі строгим JSON: коментарі чи trailing commas у налаштуваннях
виправте вручну. Старий Qwen-обгортник `~/.qwen/hooks/wiki-session-start.sh` після
оновлення не потрібен; інсталятор його не видаляє — перевірте посилання й приберіть вручну.

## Видалення

```bash
bash "$HOME/.claude/skills/wiki/uninstall.sh"
```

Прибирає лише власні посилання й реєстрації хуків. `--remove-clones` видаляє ще й
Git-клони, якщо на них не лишилося посилань. Вікі та `AGENTS.md` ваших проєктів
не видаляються.
