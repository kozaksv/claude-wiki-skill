# W1 — Git-база до змін: pre_change_git_anchor

**W1 spec r1 — чернетка для рев’ю. Дата: 25.10.2026.** Це контракт майбутньої реалізації, а не опис уже готової runtime-функції.

[Основна специфікація W1](../../2026-10-25-wiki-watchdog-w1-contracts.md) · [Контрактні сценарії](../../../../tests/fixtures/watchdog-contracts/v1/contract-cases.json)

Джерела: [RFC v5, §11.5 та AC24](https://github.com/kozaksv/claude-wiki-skill/issues/21), [P2-2 рев’ю декомпозиції](https://github.com/kozaksv/claude-wiki-skill/issues/23#issuecomment-6393600114).

## 1. Відповідальність і гарантії

W1 визначає контракт. W2 записує й зберігає `pre_change_git_anchor`, коли має підтверджену придатну межу до зміни файлів. W5 читає цей запис і успішні квитанції журналювання для окремих шляхів, визначає базу порівняння та керує підготовкою і завершенням операції журналу.

Anchor визначає нижню межу одного спостережуваного інтервалу. Він не доводить, що всі попередні коміти вже журналювалися або що всі зміни в інтервалі належать одному агенту. Поточний HEAD, час чи автор коміту, відсутність квитанцій і чистий стан після зміни не замінюють цієї межі.

Збережений anchor незмінний. Пізніший чистий HEAD, повтор discovery, compact, replay або невдалий log append не пересувають його вперед. База успішно залогованого шляху просувається через його квитанцію; інші шляхи зберігають попередню базу.

## 2. Спільний запис

Нижче наведено семантичну схему. Фізичні таблиці SQLite й міграції визначає W2.

```text
PreChangeGitAnchor {
  contract_version
  anchor_id
  scope: {
    user_scope, harness, canonical_worktree_id, wiki_id,
    session_id, agent_id, interval_id
  }
  capture_epoch                  // provenance; не лічильник скидання/строку дії
  capture_generation
  source: {event_id, source_id, source_cursor, boundary_kind}
  provenance: observed
  git: {
    object_format, head_oid, tree_oid,
    worktree_identity, wiki_relative_path
  }
  coverage: {
    path_scope, clean_index, clean_worktree, untracked_state,
    stable_head_observed
  }
  captured_order                 // локальний порядок/cursor; час діагностичний
  reason
}
```

- Git OIDs перевіряються відповідно до формату об’єктів репозиторію. Фіксована довжина SHA-1 не є універсальним контрактом.
- `path_scope` визначає зафіксовану область вікі. Він не поширюється автоматично на весь remote-репозиторій чи інші worktrees.
- `source` ідентифікує межу, спостережену до змін, які покриває запис. Саме існування полів не означає, що конкретний адаптер уже довів таку capability.
- Unknown/read-error відрізняється від відсутності. Недоступні tree/parent не прирівнюються до порожнього Git-дерева.
- Квитанція W5 посилається на `anchor_id`, якщо він використаний, і зберігає визначений before/after-state для кожного шляху, версію бази та Git watermark. Вона не залежить від змінного «останнього HEAD».
- Pending-операція фіксує точну версію anchor/receipt. Retention не може мовчки замінити її новішою базою.
- `capture_generation` зберігає походження запису. Disable не видаляє валідну Git-базу: явно викликаний offline helper може використати її або квитанцію в тому самому worktree/wiki, не активуючи hooks чи API jobs.

Підтверджений справжній root commit можна зіставити з порожнім деревом за правилом RFC v5. Shallow commit із недоступним parent не є root commit. Відсутність HEAD у ще не закоміченому worktree сама собою не робить чистими вже створені untracked-файли вікі.

## 3. API фіксації та умови придатності

```text
capture_pre_change(scope, boundary_evidence)
  -> Captured(anchor_id) | Existing(anchor_id) | NotCaptured(reason)

get_log_baseline(scope, explicit_paths)
  -> BaselineView {
       per_path_successful_receipt_versions,
       eligible_anchor?,
       generation,
       conflict_or_unknown_reasons
     }
```

W2 може автоматично зафіксувати anchor, якщо одночасно виконані такі умови:

1. Відомі ідентичність worktree/wiki та атрибуція джерела; вікі ініціалізована.
2. Адаптер/профіль або початкова межа сесії підтверджують, що фіксація передує першій релевантній мутації цього інтервалу. Допустимі чистий початок сесії чи discovery з підтвердженою причинною межею до tools, або перевірений pre-tool hook. Довільний пізній discovery не є таким доказом.
3. Git-об’єкти та стан репозиторію доступні. Wiki-scope чистий у index і worktree, без нез’ясованого релевантного untracked-вмісту.
4. HEAD і стан області узгоджені протягом фіксації. Виявлена гонитва повертає `NotCaptured`.
5. Немає невирішеної неоднозначності володіння чи інтервалу для нової бази. Попередня pending-операція залишається прив’язаною до своєї бази.

Чистота перевіряється в області вікі. Незалежний змінений файл поза нею не зобов’язаний блокувати фіксацію. Шлях за межами `coverage` не може запозичити цей anchor.

Фіксація використовує обмежений бюджет обробки події W2. Timeout або невідома pre-change capability означають відсутність автоматичного anchor і не блокують звичайну роботу агента. Worker, який прочитав поточне дерево вже після мутації, не створює доказу стану до неї. Сам лише `PostToolUse` із чистим поточним HEAD недостатній.

Адаптер без доведеної придатної межі все одно може працювати з W5 через успішні квитанції або явні base/commit/range. W1 не вимагає завершення live runtime-перевірок усіх профілів хуків: невідоме позначається явно й має цей fallback. Перевірка capability конкретного профілю належить W7–W9.

Фіксація ідемпотентна для спостереженої події/інтервалу. Replay та паралельний discovery повертають наявний anchor, не створюючи нові версії інтервалу.

## 4. Вибір і використання бази

Спочатку W5 узгоджує наявну pending-операцію. Для кожного явно переданого шляху підтверджена успішна квитанція має пріоритет над автоматичним anchor або переданою історією Git. Коміт уже залогованого вмісту не створює ще одного запису.

Якщо квитанція не дає потрібної бази, W5 використовує придатний anchor або явний `--base` / `--commit` / `--range`. Ці параметри визначають історію в поточному виклику. Окремий `op begin` чи ручний operation ID не потрібні.

Для відомого інтервалу W5 визначає before-state через відповідне попереднє дерево або parent першого належного до інтервалу коміту. Потім порівнює явно передані шляхи з їхнім поточним вмістом і станом існування, включно з незакоміченими змінами. Інші шляхи не додаються до операції автоматично. Mutation IDs уточнюють атрибуцію, але їхня відсутність не заважає shell, генераторам або offline helper, якщо база вмісту відома.

Anchor, створений на новому SessionStart, не є базою для операції до `captured_order` цього інтервалу. Якщо належність операції до охопленого інтервалу не підтверджена, потрібні receipt або explicit base/commit/range; інакше результат — `needs_baseline`, а не `unchanged`.

Коли придатної нижньої межі немає, W5 повертає `pending: needs_baseline`, зберігає durable operation ID та показує конкретне продовження через base/commit/range. Повтор із цими даними продовжує ту саму pending-операцію. W5 не може після вже виконаного commit викликати discovery, прийняти поточний HEAD за новий before-anchor і повідомити `unchanged` щодо попередньої зміни.

Одна операція може охоплювати лише частину шляхів anchor. Її квитанції просувають базу тільки цих шляхів. Журналювання сторінки P не повинно пересунути спільну нижню межу за незалоговані зміни сторінки Q. Тому наступна змішана операція може використовувати квитанцію P та початковий anchor для Q.

## 5. Зміна стану, непридатність і паралельність

| Ситуація | Обов’язковий результат |
|---|---|
| Повтор discovery на новішому чистому HEAD після мутації | Зберегти початковий anchor; поточна чистота його не замінює |
| Підтверджений compact/resume того самого інтервалу | Зберегти базу/anchor pending-операції; epoch сам його не скидає |
| Непідтверджений resume, fork, інший clone/worktree/wiki | Не успадковувати anchor за remote URL чи схожим шляхом; потрібна валідна квитанція, явна база або pending |
| Недоступний parent/tree, неоднозначний merge/rename, diverged history | Pending із конкретною причиною; без вгадування first parent чи порожнього дерева |
| Виявлений нез’ясований зовнішній overlap у зміненому шляху | Pending, доки квитанція або явна історія не розв’язує атрибуцію; anchor не доводить власника змін |
| Помилка журналу, crash, частковий append/rotation | Зберегти початкову базу операції; recovery її не пересуває |
| Підтверджене завершення журналювання та запис успішної квитанції | Просунути базу лише шляхів цієї квитанції |
| Нова непов’язана сесія чи epoch із чистим HEAD | Не стирати старі pending-докази й не покривати попередні зміни заднім числом |
| База втрачена через допустимий retention | Повідомити unavailable; не переозначувати відсутність як unchanged/handled |

W2 надає версійне читання бази та compare-and-swap примітив її фіксації під час підготовки операції. Узгоджена для W5 серіалізація writers на рівні вікі охоплює підготовку, append і завершення. Якщо інший helper змінив версію квитанції, другий helper перечитує базу до підготовки нової операції; він не продовжує diff від застарілого anchor.

Версія бази — сукупність фактично використаних посилань на per-path receipt/anchor, а не лише кінцевий hash. Це зберігає окремі залоговані A→B→A→B як різні операції, а повтор того самого change set повертає наявну операцію.

Filesystem/Git і SQLite не утворюють одну атомарну транзакцію. На межі запису W5 повторно перевіряє спостережений стан; виявлена гонитва йде чинним шляхом bounded retry/pending. Контракт не гарантує взаємного виключення зі стороннім writer, який ігнорує lock. Це технічна перевірка консистентності, без додаткового модельного review після простого ремонту.

Новий підтверджений інтервал може отримати новий anchor, лише не переприв’язуючи pending-операцій і не втрачаючи ще потрібних баз окремих шляхів. Старі записи, на які є посилання, залишаються незмінними. Політику retention та індексування уточнюють спеки W2/W5; нових числових лімітів цей annex не вводить.

## 6. Контрактні сценарії та межа доказу

[Contract cases](../../../../tests/fixtures/watchdog-contracts/v1/contract-cases.json) містять синтетичні приклади для приймання W2/W5. Вони визначають очікувані рішення та зміни квитанцій, але не є runtime captures або підтвердженням Rust-реалізації.

Мінімальне покриття:

- clean pre-change capture → edit → commit → helper;
- first use після commit без anchor → needs_baseline → явне продовження тієї самої pending-операції;
- пізній чистий PostToolUse/discovery без доказу before-state;
- dirty wiki при discovery та незалежний dirty файл поза wiki-scope;
- повтор discovery, compact і log failure без пересування бази;
- receipt → commit → ідентичний retry без нового запису;
- часткові per-path receipts та конфлікт версії між двома helpers;
- відсутній parent на shallow boundary і окремо справжній root commit;
- інший worktree, невстановлений resume та зовнішній overlap;
- різні operation IDs для окремо залогованих A→B→A→B.

Наявні AGY captures не доводять доступності та точного часу фіксації для всіх pre-change hook-профілів. Для неперевірених профілів capability залишається unknown; W7–W9 збирають власні докази, а receipt/explicit fallback зберігає функціональність helper.
