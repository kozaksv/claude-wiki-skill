# W1 — спільний фрагмент checkpoint з обмеженням розміру

**Статус: W1 spec r1, чернетка для рев’ю.** Описує контракт майбутньої реалізації.

Основна спека: [Спільні контракти Wiki Watchdog W1](../../2026-10-25-wiki-watchdog-w1-contracts.md). Синтетичні приклади: [contract-cases.json](../../../../tests/fixtures/watchdog-contracts/v1/contract-cases.json).

Основа: [RFC v5 #21](https://github.com/kozaksv/claude-wiki-skill/issues/21), §§6.1–6.3, 7, 8 та AC08/AC11/AC17/AC30; [план #23](https://github.com/kozaksv/claude-wiki-skill/issues/23) і [уточнення P2-3](https://github.com/kozaksv/claude-wiki-skill/issues/23#issuecomment-6393600114). Числові ліміти й граф залежностей зберігаються.

## 1. Відповідальність компонентів

- **W1** визначає `BoundedCheckpointFragment/v1`, типи джерел і курсорів, стани захоплення тексту, правила спільного бюджету та контрактні приклади.
- **W2** реалізує спільний примітив обмеженого читання й відбору, межу очищення даних, атрибуцію джерел і тимчасове зберігання фрагментів із TTL. Helper не потребує мережі або Jev.
- **W7/W8/W9** зіставляють payload і записи transcript конкретної версії харнеса з дозволеними джерелами; доводять їхню свіжість, належність поточному агенту й поточному завершенню. Усі використовують helper W2.
- **W3** споживає той самий фрагмент для локального префільтра й fallback у M1/M2. Рішення, чи є зміст кандидатом для нагадування, належить W3.
- **W10** поєднує цей фрагмент із відібраними уривками вікі у context pack до 16 KiB, виконує локальний пошук і оцінювання через Jev. W10 володіє пакетом та оцінювачем; базове захоплення head+tail належить W2.
- **W4** може показувати покриття захоплення та причини прогалин у звітах. Недоступний хвіст не зараховується як успішне повне захоплення.

## 2. Дві незалежні межі

1. Фрагмент checkpoint містить **до 4096 Unicode scalar values нового матеріалу сумарно** в усіх збережених сегментах користувача, моделі й інструментів. Це одна квота на фрагмент, а не окрема квота кожному джерелу, head чи tail.
2. Повний очищений **context pack W10** має розмір до **16 384 UTF-8 bytes**, включно з його метаданими джерел, прогалин, обрізання та уривками вікі. Ця межа може зменшити доступну символьну квоту. Інструкції й критерії API-запиту поза context pack мають власні обмеження та входять до резервування всього API input/cost за §8 RFC.
3. Спільний helper приймає нижчу ефективну квоту scalars і, за потреби, нижчу байтову квоту результату від споживача. Споживач не може підвищити стелю профілю 4096. Рахуються валідні Unicode scalar values; довжина у UTF-16 units або UTF-8 bytes не замінює цей підрахунок. Нормалізація Unicode лише для вміщення у квоту не виконується.
4. Виключені джерела й секрети фільтруються **до** остаточного відбору head/tail і підрахунку обсягу. Текст заміни після redaction займає scalars/bytes на загальних підставах. Очищення не обіцяє виявлення довільного секрету.
5. Мінімального порога довжини для змістовного кандидата немає. Коротка вказівка або фінальний висновок можуть бути кандидатом; великий tool output сам не доводить цінності знання.
6. Збережені 4096 scalars не означають повного обсягу нового модельного контексту. Оцінювач consultation aging у W3 використовує окремі перевірені інкрементальні token evidence і стан покриття. Обрізана вибірка не підміняє оцінки всього нового контексту.

## 3. Джерела, позиції та ідентичність матеріалу

### 3.1. Посилання на джерело

Посилання визначає точне дозволене джерело у поточному scope користувача, харнеса, worktree, вікі, сесії й агента. Воно містить:

- `source_id`, тип джерела (`user_text`, `model_final`, `tool_result`, `change_evidence`), відому native identity події або запису, версію/watermark джерела та provenance.
- `locator` — **типізовану native-позицію за версійним профілем**. Приклади: event ID payload і JSON field; identity transcript та step ID/field; byte range файла й підтверджена identity запису. Byte cursor, step index та scalar offset не є взаємозамінними.
- Атрибуцію свіжості й поточного завершення (`current`, `stale`, `unknown`) та атрибуцію поточного агента. Доступність джерела й успішна атрибуція — окремі ознаки.
- `sanitizer_version`, покриття прочитаного джерела та факт спостереження його справжнього початку/кінця.

Кожен повернений текстовий сегмент має власне посилання на джерело, `part: whole|head|tail`, scalar-позицію в **очищеному представленні джерела** й точний відібраний текст.

### 3.2. Одиниці й початок відліку

Компактний формат scalar-позиції:

```json
{
  "basis": "sanitized_source",
  "unit": "unicode_scalar",
  "origin": "start",
  "offset": 0,
  "length": 2048
}
```

Якщо reader отримав справжній хвіст без сканування всього попереднього тексту, він використовує `origin: end` із підтвердженим кінцем джерела. Offset 0 і length L означають останні L scalars у звичайному порядку тексту. За відомої загальної довжини N це діапазон [N−L, N); offset d означає [N−d−L, N−d). Невідома загальна довжина лишається `null`. Абсолютний scalar offset не виводиться з byte offset; захоплений prefix не позначається як tail.

Native offsets джерела та offsets очищеного представлення зберігаються окремо: redaction може змінити довжину. При повторному отриманні тексту споживач перевіряє версію/watermark джерела й версію sanitizer та відтворює відповідне очищене представлення в межах дозволеного читання. Застосовувати очищений scalar offset безпосередньо до raw JSON або неочищених bytes не можна. Коли адаптер не може вказати коректний початок відліку, він фіксує unknown/limited, а не offset 0.

### 3.3. Матеріал і його представлення

Контракт розділяє:

- **Content identity матеріалу** належить незмінному `MaterialRef` із C06: `material_id`, `source_refs`, `source_versions`, `covered_source_ranges` та `identity_basis` визначають логічний матеріал і підтверджені події/версії його джерел.
- **Source watermarks для content identity** — позиції й версії підтверджено спостереженого матеріалу, зафіксовані у відповідних незмінних `MaterialRef` через версії й покриті діапазони джерел. Вони потрібні для dedup і свіжості. Окремі `Checkpoint.source_watermarks` із C06 фіксують поступ групування матеріалу; фрагмент не створює їхньої другої копії.
- **`representation_fingerprint`** належить `RepresentationRef` із C06 і описує конкретне відібране очищене представлення: сегменти, їхнє покриття, версії sanitizer/selector і застосовані квоти.

Назва `material_fingerprint` у цьому поясненні означає відбиток content identity й перевірених source watermarks відповідних незмінних `MaterialRef`; це не додаткове поле `BoundedCheckpointFragment`. Він **не визначається лише хешем обрізаного тексту** й не включає зміну квоти або redaction як доказ нового знання. `RepresentationRef.representation_fingerprint` може змінитися при іншому відборі того самого матеріалу; це дає підставу перевірити актуальність кешованої оцінки, але не створює нового knowledge checkpoint, need або резерву continuation/delivery.

Нове підтверджене джерельне свідчення може змінити material evidence за правилами checkpoint основної спеки. Саме розширення представлення, отримання раніше недоступного хвоста або зміна правил очищення не поновлюють використаний Stop guard цього логічного checkpoint. Невідома неперервність джерела залишається unknown.

Фрагмент додатково містить:

```text
checkpoint_id
material_refs[]                      # незмінні MaterialRef за C06
representation_ref                   # RepresentationRef за C06, включно з representation_fingerprint
segments[]
retained_scalar_count
retained_utf8_bytes
truncated: bool
gaps[]                              # джерело й відомі межі; невідомий розмір явний
omitted_sources[]                    # IDs/типи/причини, без raw content
final_text_status: available|limited|unavailable
limitations[]                       # stale_final, tail_unavailable, read_limit, invalid_encoding
```

Це та сама форма `BoundedCheckpointFragment`, що й у C09; структури за посиланнями визначено у C06. `sanitizer_version`, `selector_version` і `representation_fingerprint` беруться з `representation_ref`. Типи, одиниці й відмінність unknown є обов’язковими. Відбиток обмеженого представлення не доводить незмінність неспостереженої решти джерела; покриття лишається частиною provenance.

## 4. Послідовність читання й відбору

1. Визначити дозволене джерело та підтвердити його зв’язок із поточною подією/завершенням. Самої згадки шляху іншого агента у tool string недостатньо для відкриття його transcript.
2. До відбору кандидатів виключити відомі службові записи за походженням. Для AGY це власні `SYSTEM_SDK/EPHEMERAL_MESSAGE`, власний Stop feedback і службові `SYSTEM_MESSAGE`. Native `SYSTEM/CHECKPOINT` є lifecycle evidence. Використовувати native source/provenance; не видаляти сліпо користувацький текст із подібними підрядками.
3. Читати в межах явних лімітів I/O, розміру запису й часу життя reader профілю. Reader із підтримкою tail має отримати справжній кінець релевантного поточного джерела. Читання довільного повного transcript із подальшим обрізанням не є bounded capture.
4. Очистити дозволене представлення до відбору результату. Для redaction на межі вікна потрібен достатній обмежений контекст для вибраних правил; інакше вікно позначається unavailable/limited. Розрив шаблону на межі I/O-вікна не дозволяє пропустити виключений фрагмент.
5. Розподілити **спільну квоту checkpoint** між вибраними джерелами. Producer задає детермінований порядок/правило відбору й фіксує пропущені джерела. Він не склеює незалежні фрагменти по 4096 scalars. Свіжий фінальний висновок і релевантна вказівка користувача мають враховуватися; останнього службового підтвердження недостатньо.
6. Для вибраного довгого final початково виділити половину його квоти head і половину tail; непарний залишок scalar може отримати tail. Коротке джерело зберегти один раз. Head і tail не перекриваються та не рахуються двічі. Межі scalars зберігаються; межам абзаців надається перевага зміщенням усередину, без перевищення квоти. Пропущена середина має явні метадані, а не вигаданий текст джерела.
7. Одночасно застосувати нижчу байтову квоту, якщо вона задана, зберігши обидва кінці за їхньої доступності та позначивши додаткові пропуски. Для повного context pack W10 визначити одне канонічне серіалізоване UTF-8 представлення й рахувати bytes разом із його метаданими/escaping. Зовнішній provider envelope — окремий API overhead. Додавання уривка вікі не може перевищити межу пакета 16 384 bytes.
8. Зберігати лише тимчасові очищені фрагменти й source/cursor metadata. Raw full transcript або повне оточення не потрапляють у SQLite/logs. Сплив TTL чи неможливість повторного читання — `expired/limited`, а не `handled`.

Детальна спека реалізації W2 має визначити обмеження I/O/record і поведінку відновлення. W1 не вводить ще одного універсального числового ліміту. Джерело, яке не можна коректно прочитати/декодувати в цих межах, лишається limited/unavailable; це не блокує локальний облік і не створює приводу для нового continuation.

## 5. Некоректний, відсутній та обрізаний вхід

- `null` final text, відсутнє поле, старе завершення, unknown current-agent mapping і недоступний transcript — різні limitations. Вони не підміняються попередньою відповіддю чи висновком із кількості читань.
- Helper приймає валідні послідовності Unicode scalars. Некоректний UTF-8, непарні JSON surrogates і неповні записи відхиляються для відповідного представлення джерела з позначкою `invalid_encoding/limited`. Інші незалежно валідні джерела можуть зберігатися. Мовчки видалити некоректні bytes і оголосити final повним не можна. Розрив валідної UTF-8 послідовності на межі chunk допускає обмежене дочитування межі; нерозв’язаний випадок лишається limited.
- Відома пропущена середина означає `truncated=true`. Недоступний справжній хвіст додатково означає `final_text_status=limited` і `tail_unavailable`; це не успішний head+tail.
- Позитивне локальне свідчення у збереженому фрагменті може обґрунтувати кандидата за правилами політики. Прогалина не обґрунтовує категоричне `no new knowledge` або `not in wiki`. Jev отримує явні limitations і може повернути `insufficient_evidence`.
- Redaction, власний feedback, replay і відомий матеріал не стають новим змістом лише через зміну тексту представлення або його fingerprint. Dedup спирається на content identity й source watermarks. Зміна квоти відображення сама не поновлює Stop continuation чи delivery credit.

## 6. Межі AGY, пов’язані з цим контрактом

Ці правила повторюють погоджений план:

- `PreInvocation`, який запускає execution стискання, непридатний для доставки ще до reservation. Він не витрачає delivery units і не просуває retry cooldown.
- Успішний compact потребує нового native `SYSTEM/CHECKPOINT`; текст `/compact` сам не відкриває epoch. Pending потреби зберігаються.
- Suppression обмежене execution. Невдалий compact зі stale `lastUserInput` не може назавжди вимкнути всі подальші ходи.
- Scheduled delivery і лічильник трьох нових меж для retry використовують підтверджені межі нового ходу/пробудження. `invocationNum==0` — сигнал профілю, а не унікальна identity, доказ root-role чи самодостатній доказ нового користувацького ходу.
- Кроки tool-loop з `invocationNum>0` не просувають звичайний retry й не доставляють старі pending потреби. Лишається вузький виняток консультації при першому вході в новий wiki-scope, зі спільними caps і child guards.
- Власний Stop continuation, replay і unknown boundary identity не зараховуються як новий поступ retry.

## 8. Контрактні приклади

[Синтетичні fixtures](../../../../tests/fixtures/watchdog-contracts/v1/contract-cases.json) відокремлені від native captures. Вони задають такі очікування:

| Випадок | Очікуваний результат |
|---|---|
| Коротке рішення українською | Проходить без порога довжини |
| Astral characters на межі 4096 | Один валідний scalar рахується один раз; сума head і tail до 4096 |
| Combining marks | Scalars рахуються без нормалізації Unicode; bytes/surrogates не розриваються |
| Висновок лише у справжньому хвості | Відібраний tail містить висновок; пропущена середина позначена |
| Кілька нових джерел | Одна спільна квота, пропуск джерела явний |
| Byte cap нижчий за scalar cap | Менший результат, валідний Unicode, явне обрізання |
| Redaction на межі обрізання | Секрет вилучений до відбору за квотою; prefix не витікає |
| Null/stale final | Unavailable/limited, без повторного використання попередньої відповіді |
| Prefix-only capture PR22 | Tail лишається недоступним; підтримка head+tail не заявляється |
| Лише service/replay матеріал | Сам feedback або compact summary не створюють нового кандидата |
