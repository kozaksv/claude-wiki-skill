# Spec — Wiki Skill v4.6.0: нативна підтримка Qwen Code

**Дата:** 2026-08-13
**Версія скіла:** 4.5.1 → 4.6.0 (behavior release; `wiki_version` лишається `"4.0"` — нуль міграцій для існуючих вікі)
**Джерело:** брейншторм-сесія `docs/superpowers/specs/2026-08-13-v46-qwen-design.md` (затверджено користувачем)
**Slug циклу:** `v46-qwen`. База: `origin/master`.
**Ревізія:** враховано два P1 із «Відкладеного рев'ю» дизайн-документа —
first-match-wins замість union у stdin-екстракторі (R9) і orphaned-hook guard
`uninstall.sh` поверх обох settings-файлів (R10).

## Проблема

Скіл декларує підтримку Claude Code / Codex / Gemini CLI, але Qwen Code —
четвертий реальний клієнт користувача — тримається на саморобних адаптерах поза
репозиторієм. Три конкретні поломки:

1. **Телеметрія мовчки не пишеться.** `~/.qwen/settings.json` реєструє
   PostToolUse з matcher `read_file|write_file|edit|notebook_edit`, хук
   запускається й отримує коректний stdin, але `hooks/post-tool-use.sh:312-316`
   знає лише Claude-назви (`case "$tool_name" in Read) … Edit|Write|MultiEdit) …
   *) exit 0`). Кожен Qwen-виклик виходить через `*) exit 0` — `view_count` /
   `patch_count` / `_hooks.post_tool_use_at` не рухаються. Пріоритизація lint
   (top-N most-viewed/most-edited) у Qwen-сесіях працює наосліп, як до v4.5.
2. **Session-Start Contract тримається на зовнішньому wrapper-і.** Qwen не
   інжектить не-JSON stdout у контекст (перетворює на «info»-повідомлення), тож
   канонічний `hooks/session-start.sh` сам по собі там марний. Працює лише
   `~/.qwen/hooks/wiki-session-start.sh` — файл поза репо, поза версіонуванням,
   поза un/install, з hardcoded шляхами; ламається на будь-якому перевстановленні
   й невидимий для `wiki doctor`.
3. **Discovery й експорти не бачать Qwen.** `_wiki_disc_dir_pointers`
   (`hooks/lib/discover.sh:93`) перебирає лише `CLAUDE.md AGENTS.md GEMINI.md`
   — resident-файл `QWEN.md`, який Qwen Code читає нативно, ігнорується;
   `discover_wiki` fallback знає лише `$CLAUDE_PROJECT_DIR`; `install.sh` експортує
   скіл у `~/.agents/skills` і `~/.gemini/skills`, але не в `~/.qwen/skills`.

Тобто v4.5-механіка (хуки замість слухняності моделі) в Qwen-сесіях деградує рівно
до тієї текстової дисципліни, яку v4.5 і мав замінити.

## Підхід

Qwen стає **четвертим клієнтом за зразком трьох існуючих** — bounded-розширення
наявних потоків, нуль нових концепцій:

- **Один тонкий транспорт-шар, нуль дублювання логіки.** Уся канонічна логіка
  (discovery, boundary-guard, version-gate, JSON r-m-w телеметрії, інжект індексу)
  лишається там, де вона є. Qwen-специфіка — рівно два місця: новий
  `hooks/session-start-qwen.sh` (~30 рядків: викликати сусідній канонічний хук і
  вдягнути його stdout у Qwen JSON envelope) і кілька точкових union-розширень
  таблиць назв (tool-names, ключі stdin, імена instruction-файлів, env-змінні).
- **Union, а не branch.** Ніде не з'являється `if qwen … else claude …`: до
  наявних **переліків** (tool-names, instruction-файли, settings-файли,
  env-змінні) додаються Qwen-значення. Claude/Codex/Gemini проходять ті самі
  гілки, що й до зміни — регрес-нуль за конструкцією, а не за тестом.
  **Виняток — вибір шляху зі stdin:** там union семантично невірний
  (однофайловий tool call ≠ кілька лічильників), тому скалярні ключі
  резолвляться first-match-wins; деталі й обґрунтування — нижче.
- **Мультиклієнтський інсталер замість другого скрипта.** `install-hooks.sh` /
  `uninstall-hooks.sh` рефакторяться в параметризовану функцію «register/strip
  into settings-file», яка викликається двічі (claude, qwen) з тим самим
  lock/backup/merge/atomic-write протоколом, окремим lock-ом на кожен файл.
- **Глобальна топологія без per-project розкатки** — як у v4.5: записи в
  `~/.qwen/settings.json` вказують на **канонічні** шляхи
  `$HOME/.claude/skills/wiki/hooks/…`, тож маркер `/skills/wiki/hooks/` лишається
  єдиним для granularity un/install; проєктні репо чисті від агент-специфіки.
- **On-disk схема вікі не змінюється.** Ні полів, ні міграцій, ні bump-у
  `wiki_version`.

## Зміни

Проєкція для скіла (як у v4.5-спеці): **дані = схема вікі на диску + `.usage.json`**,
**API = контрактні файли скіла (SKILL.md + `references/`) + hook-скрипти + інсталери**,
**UI = діалоги агента (doctor-звіт, install-summary, lint-checks, шаблони планів)**.

### Дані

**Без змін.** `wiki_version` = `"4.0"`. `.usage.json` — та сама схема, ті самі
10 полів запису, той самий зарезервований `_hooks` мета-ключ
(`session_start_at`, `post_tool_use_at`, `last_lint_at`, `hook_version`). Qwen
пише в ті самі лічильники тими самими функціями. Нуль міграцій, нуль backfill.

### API — hook-скрипти

**`hooks/session-start-qwen.sh` (новий).** Логіка зовнішнього
`~/.qwen/hooks/wiki-session-start.sh` переїжджає в скіл:

- `HOOK_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` → викликає
  `"$HOOK_DIR/session-start.sh"` (сусідній канонічний, **ніколи** hardcoded
  `$HOME/...`), захоплює його stdout.
- Порожній stdout (нема вікі / discovery не резолвнув / хук сам вирішив мовчати)
  → **нічого не друкує** й `exit 0`. Порожній envelope створив би шумове
  «info»-повідомлення в кожній сесії без вікі.
- Непорожній stdout → `python3 json.dumps` пакує його в
  `{"continue":true,"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}`
  одним рядком у stdout.
- Немає `python3` → тихий `exit 0` (той самий fail-open, що й скрізь у v4.5).
- stderr дочірнього хука не потрапляє в stdout (діагностика лишається в stderr
  wrapper-а — Qwen її не парсить).
- Кожен шлях завершується `exit 0`; wrapper ніколи не блокує старт сесії.
- Файл лежить у `hooks/`, тож його канонічний шлях містить маркер
  `/skills/wiki/hooks/` — granularity un/install працює без змін.
- **`hooks/session-start.sh` не змінюється взагалі** (Claude-шлях недоторканий:
  24 KB cap, untrusted-data преамбула, lint-reminder, `_hooks` heartbeat — усе
  успадковується як є).

**`hooks/post-tool-use.sh` — три точкові union-правки:**

- `case "$tool_name"`: `Read|read_file) action="view"` ;
  `Edit|Write|MultiEdit|write_file|edit|replace|notebook_edit) action="patch"`.
  Claude-назви лишаються першими й незмінними. `replace` — legacy-alias `edit`
  у Qwen; включається в case, бо коштує нуль, а без нього втрата тиха.
- Python-екстрактор stdin (`add()`-ланцюжок) — **два різні режими для двох
  різних за семантикою джерел, це не одна union**:
  - **Скалярні ключі — first-match-wins, а НЕ union.** Рівно один
    «первинний шлях» береться з ланцюжка
    `tool_input.file_path` → `tool_input.notebook_path` → `tool_input.path`:
    перший непорожній рядок виграє, решта ключів **не читаються**. Це дослівно
    повторює власний ланцюжок екстракції Qwen (перевірений факт №2 дизайну) і
    прямо випливає з того, що всі чотири matched-інструменти
    (`read_file`/`write_file`/`edit`/`notebook_edit`) — **однофайлові**: один
    tool call має бампати рівно один лічильник. Union тут був би багом:
    `tool_input` з кількома валідними ключами (штатно — `path` як legacy-дубль
    `file_path`; ворожо — підкинутий зайвий ключ) оновив би кілька записів
    `.usage.json` за один виклик, тихо роздуваючи телеметрію.
  - **`tool_input.edits[].file_path` лишається адитивним union** поверх
    первинного шляху, з наявним порядок-стабільним dedup через `seen` — це
    свідомо мультифайлова batch-семантика Claude-форми, і саме тут кілька
    бампів за виклик коректні. Ця гілка не змінюється взагалі.
  - **Для Claude поведінка не змінюється — але не тому, що ключа немає.**
    `tool_input.path` у Claude-payload-ах **існує** (`Glob`, `Grep`), тож
    твердження «цих ключів у Claude-матчерах немає» хибне і як обґрунтування
    не використовується. Реальні дві незалежні причини:
    1. **Зареєстрований matcher.** Claude-entry `PostToolUse` лишається
       `Read|Edit|Write|MultiEdit`, тож `Glob`/`Grep` хук взагалі не
       викликають — payload із `path` до екстрактора не доходить.
    2. **Action-gate.** Навіть якщо такий payload дійде (чужі або руками
       правлені settings, ширший matcher), `case "$tool_name"` падає в
       `*) exit 0` **до** anchor-резолюції, `discover_wiki` і будь-якого
       запису в `.usage.json`. Раніше такий виклик виходив на перевірці
       порожнього `file_paths`, тепер — на action-gate; обидві гілки дають
       `exit 0` без побічних ефектів і без stdout.
  - **Щоб цей інваріант був структурним, а не побічним,** action-gate
    (`case "$tool_name"` разом із гілкою `*) exit 0`) переміщується **вище**
    перевірки `[ "${#file_paths[@]}" -gt 0 ]`. Перше рішення після парсингу
    stdin — allowlist імен інструментів; результат екстрактора взагалі
    розглядається лише для дозволених імен. Набір гілок, значення `action` і
    коди виходу не змінюються.
  - Для matched Claude-інструментів `file_path` присутній завжди, тож
    first-match-wins зупиняється на першій ланці ланцюжка і
    `notebook_path`/`path` для них не читаються ніколи.
- Anchor precedence: `CLAUDE_PROJECT_DIR → QWEN_PROJECT_DIR → stdin cwd → pwd`
  (Qwen експортує обидві змінні, але на compat-експорт не покладаємось).
  Відносний `path` резолвиться наявним anchor-механізмом, боундарі-гард і
  version-gate — ті самі, без послаблень.

**`hooks/lib/discover.sh` — дві union-правки:**

- `_wiki_disc_dir_pointers`: `for name in CLAUDE.md AGENTS.md GEMINI.md QWEN.md`
  (append у **кінець** — пріоритет наявних файлів не змінюється; перший
  валідний pointer виграє, як зараз).
- `discover_wiki` fallback стартової точки: `CLAUDE_PROJECT_DIR →
  QWEN_PROJECT_DIR → pwd`.
- Fail-closed-без-git, boundary-guard, normalize-pointer, Phase-2 fallback —
  без змін.

`hooks/lib/version-gate.sh` — **без змін.**

### API — інсталери

**`hooks/install-hooks.sh` → параметризована функція
`register_into <settings_file> <client>`** з тим самим протоколом, що зараз:
mkdir-lockdir мутекс → read-under-lock → timestamped backup → python3-merge по
маркеру → atomic tmp + `os.replace`. Виклики послідовні:

| клієнт | settings-файл | lock | SessionStart | PostToolUse |
|---|---|---|---|---|
| claude | `~/.claude/settings.json` | `…/settings.json.lockdir` | matcher `startup\|clear\|compact` → `…/hooks/session-start.sh` | matcher `Read\|Edit\|Write\|MultiEdit` → `…/hooks/post-tool-use.sh` |
| qwen | `~/.qwen/settings.json` | `~/.qwen/settings.json.lockdir` | matcher `startup\|clear\|compact` → `…/hooks/session-start-qwen.sh` | matcher `read_file\|write_file\|edit\|replace\|notebook_edit` → `…/hooks/post-tool-use.sh` |

- Claude-entries лишаються **байт-у-байт** тими самими (та сама обгортка
  `test -x "…" && "…" || exit 0`, ті самі matcher-и, той самий порядок).
- Обидва Qwen-entries вказують на **канонічні** шляхи під
  `$HOME/.claude/skills/wiki/hooks/` (не на `~/.qwen/…`), тож маркер
  `/skills/wiki/hooks/` спільний, і повторний запуск ніколи не накопичує
  дублікатів. Без полів `timeout`/`name`.
- **Gate:** qwen-крок виконується лише якщо `command -v qwen` **або** існує
  `~/.qwen/settings.json`; інакше — skip із однорядковою підказкою в stderr і
  `exit 0` (відсутність Qwen — не помилка).
- **Міграція legacy:** qwen-merge додатково стрипає з `SessionStart` усі entries,
  чий `command` містить `/.qwen/hooks/wiki-session-start.sh` — інакше після
  апдейту індекс інжектиться двічі. Сам файл wrapper-а інсталер **не видаляє**
  (rollout-крок людини).
- **Блокування беруться послідовно, ніколи не вкладено** — claude-lock
  звільняється до взяття qwen-lock. Взаємного блокування двох одночасних
  install/uninstall не виникає. Стан lock-у (`LOCK_DIR`, `LOCK_ACQUIRED_MKDIR`)
  стає per-call, EXIT/INT/TERM-trap працює з поточним lock-ом; після кожного
  виклику lock звільняється явно, не лише в trap-і.
- **Чужі ключі** (`env` із секретами, `mcpServers`, `modelProviders`, будь-що ще)
  проходять JSON round-trip незмінними за значеннями; змінюється лише
  форматування самого файла (`indent=2`) — саме як зараз у `~/.claude`.
- Per-client backup: `~/.qwen/settings.json.bak-wiki-hooks-<TS>`; `shutil.copy2`
  зберігає права джерела. Жоден вміст settings-файлів (у т.ч. секрети) не
  друкується в stdout/stderr.
- Права результуючого файла: якщо файл існував — зберегти його `st_mode`
  (`mkstemp` дає 0600 і `os.replace` мовчки звузив би права наявного
  `~/.qwen/settings.json`); якщо створюється з нуля — 0600, бо файл штатно
  містить секрети. Створення `~/.qwen/` за потреби — `mkdir -p`.
- Контракт кодів виходу зберігається: `exit 0` лише коли зроблено або
  верифіковано нічого-робити; будь-яка справжня помилка → non-zero з
  повідомленням із **префіксом клієнта** (`install-hooks: qwen: …`), щоб
  часткова невдача не читалась як загальна.

**`hooks/uninstall-hooks.sh` — дзеркально:** та сама параметризація, strip
маркера `/skills/wiki/hooks/` **і** legacy-маркера
`/.qwen/hooks/wiki-session-start.sh` з обох файлів, кожен під своїм lock-ом;
відсутній `~/.qwen/settings.json` → нічого робити для цього клієнта. Наявний
контракт «python3 відсутній, а маркер є → це помилка, не no-op» діє для обох
файлів (від нього залежить `uninstall.sh --remove-clones`).

### API — експорти скіла

**`install.sh`:** поряд із `AGENTS_SKILLS_ROOT` / `GEMINI_SKILLS_ROOT` з'являється
`QWEN_SKILLS_ROOT="$HOME/.qwen/skills"`. Симетрично й безумовно (як gemini):
`export_skill_link "wiki" "$SKILL_LINK" "$QWEN_SKILLS_ROOT/wiki"` і те саме для
`doc-extract`, якщо він є — у **повній інсталяції**, у **`--repair-exports`**, у
статус-агрегації та в `print_export_summary`-звітах (`WIKI_QWEN_STATUS`,
`DOC_QWEN_STATUS`).

**`uninstall.sh` — дві правки:**

1. **Експорти:** `remove_symlink_entry "$QWEN_SKILLS_ROOT/wiki"
   "$SKILLS_ROOT/wiki"` (+ doc-extract) у тому ж порядку «експорти раніше за
   канонічні лінки»; `rmdir "$QWEN_SKILLS_ROOT" 2>/dev/null || true` поряд із
   gemini/agents. `~/.qwen/settings.json` сам по собі не видаляється — з нього
   лише стрипаються наші entries через `uninstall-hooks.sh`.
2. **Orphaned-hook guard мусить бачити обидва settings-файли.** Скаляр
   `SETTINGS_JSON="$HOME/.claude/settings.json"` (`uninstall.sh:124`) стає
   переліком `~/.claude/settings.json` + `~/.qwen/settings.json`, а
   `grep -q "$HOOK_MARKER"` — циклом «маркер є хоча б в одному з них» (гілка
   `elif` на `:130`, повідомлення перелічує саме ті файли, де маркер знайдено).
   **Existence-guard зберігається поіменно на кожній ітерації:** наявний
   `[ -f "$SETTINGS_JSON" ] && grep -q …` не розчиняється в циклі, а стає
   `[ -f "$file" ] && grep -q "$HOOK_MARKER" "$file" 2>/dev/null` для **кожного**
   файла переліку. Це не косметика: у Claude-only чи Qwen-only середовищі
   другого файла просто немає, і `grep` по ньому повернув би ненульовий код
   (під `set -e` — обрив uninstall, без нього — хибно-порожній результат
   ітерації). Цикл лише накопичує список файлів, де маркер знайдено; відсутній
   файл — це «маркера тут немає», а не помилка й не переривання перебору.
   **Чому обов'язково:** гілка існує, щоб `--remove-clones` НЕ видаляв
   `$SKILL_DIR`, поки в settings лишаються сироти-entries — бо `$SKILL_DIR`
   хостить єдиний recovery-скрипт `hooks/uninstall-hooks.sh`. Після v4.6 маркер
   може лежати **лише** в `~/.qwen/settings.json` (користувач Qwen без
   Claude-хуків, або Claude-гілка вже прибрана). Тоді при недоступному
   uninstaller-і умова хибна → `HOOKS_FAILED=0` → клон видаляється, а
   qwen-entries лишаються назавжди без жодного способу їх прибрати
   (`test -x`-обгортка робить їх тихо-інертними, тож користувач навіть не
   помітить). Розширення переліку — єдина правка; сама механіка
   `HOOKS_FAILED`/`SKIPPED` і verified-clone-гейт (`-d "$SKILL_DIR/.git"`,
   виклик через реальний `$SKILL_DIR`, а не через attacker-впливний
   `$SKILLS_ROOT/wiki`) не змінюються.

### UI — контрактні файли й діалоги агента

### Тести

`tests/skill-contracts.sh:21` — асерт сепаратора Platform-таблиці
`^|---|---|---|---|$` → `^|---|---|---|---|---|$` (**в тому ж комміті**, що й
SKILL.md, інакше сюїта червона).

Нові кейси в `tests/hooks/run.sh`:

- **discover**: pointer лише в `QWEN.md`; пріоритет CLAUDE.md над QWEN.md при
  двох валідних; `QWEN_PROJECT_DIR` як стартова точка без `CLAUDE_PROJECT_DIR`.
- **post-tool-use**: `read_file` → `view_count`+1; `edit` / `write_file` /
  `notebook_edit` (через `notebook_path`) / `replace` → `patch_count`+1;
  відносний `tool_input.path` + `QWEN_PROJECT_DIR` anchor; свіжий
  `_hooks.post_tool_use_at`; наявні Claude-кейси зелені без правок.
  **Гард first-match-wins (обов'язковий, інакше union-баг тихо повертається):**
  один виклик із `tool_input`, що містить `file_path` **і** `notebook_path`
  **і** `path` — три РІЗНІ існуючі wiki-сторінки — бампає рівно **один** запис
  (той, що `file_path`), а два інші записи в `.usage.json` не з'являються
  взагалі (перевірка по повному переліку не-`_` ключів, не лише по лічильнику).
  Дзеркальний кейс: `notebook_path` + `path` без `file_path` → бампається
  тільки `notebook_path`. Мультифайловий `edits[].file_path` при цьому лишається
  адитивним — окремий кейс на два записи за один виклик.
  **Гард не-matched Claude-інструментів (обов'язковий):** payload `Grep` і
  payload `Glob` із `tool_input.path`, що вказує на існуючу wiki-сторінку →
  `.usage.json` лишається байт-у-байт незмінним, stdout порожній, `exit 0`.
  Це доказ, що нова ланка `path` не відкриває лічильників поза allowlist-ом
  `case "$tool_name"`.
- **session-start-qwen**: stdout парситься `json.load`; `continue == true`;
  `hookSpecificOutput.hookEventName == "SessionStart"`; `additionalContext`
  містить `=== WIKI INDEX (hook-injected) ===`; проєкт без вікі → **порожній**
  stdout, `exit 0`; відсутній python3 → порожньо, `exit 0`.
- **install/uninstall-hooks**: qwen-запис під фейковим `HOME` + PATH-стаб `qwen`
  (перевірка gate: без стаба й без файла — skip, `exit 0`); ідемпотентний
  повтор без дублікатів; legacy wrapper-entry зникає; секрети/чужі ключі
  збережені; corrupt JSON → non-zero **без запису**; strip з обох файлів.
- **install-cross-agent-links.sh / uninstall.sh**: qwen-export
  створюється / чиниться `--repair-exports` / видаляється, `~/.qwen` не
  зачіпається поза `skills/`.
- **uninstall.sh orphan-guard (регрес на видалення recovery-скрипта):** фейковий
  `HOME`, маркер `/skills/wiki/hooks/` **лише** в `~/.qwen/settings.json`
  (Claude-settings відсутній або без маркера), `hooks/uninstall-hooks.sh`
  прибрано з клону, запуск `uninstall.sh --remove-clones` → `$SKILL_DIR`
  **НЕ** видалено, у виводі попередження з іменем саме qwen-файла, exit-код
  сигналізує skip. Дзеркально: маркера немає в жодному з двох файлів →
  клон видаляється як зараз (гард не стає надто широким). Третій кейс —
  **відсутній settings-файл**: `~/.qwen/settings.json` немає взагалі,
  маркер лише в `~/.claude/settings.json` (і дзеркально) → guard відпрацьовує
  штатно, без діагностики `grep: No such file or directory` і без обриву
  перебору на неіснуючому файлі.

Канонічна повна команда без змін:
`bash tests/hooks/run.sh && bash tests/skill-contracts.sh && bash tests/install-cross-agent-links.sh && bash tests/uninstall.sh`.

## Edge-cases

1. **Порожній інжект.** Немає вікі / discovery не резолвнув → wrapper друкує
   **нічого** (не порожній envelope) і `exit 0`; інакше кожна сесія без вікі
   отримує шумове «info».
2. **Немає `python3`** у Qwen-середовищі → wrapper тихо `exit 0`; телеметрія
   так само тихо no-op (наявний інваріант v4.5).
3. **stdin wrapper-а.** Wrapper stdin не читає; дочірній канонічний хук теж не
   читає (він не парсить `source`) — зависання неможливе; stdin передається
   дочірньому як є.
4. **Розмір інжекту.** 24 KB cap застосовує канонічний хук **до** пакування;
   JSON-екранування може збільшити байти envelope — це очікувано й не змінює
   обсяг тексту, що потрапляє в контекст.
5. **Подвійна інжекція під час міграції.** Legacy-entry стрипається інсталером;
   якщо користувач не видалив сам файл `~/.qwen/hooks/wiki-session-start.sh`,
   він лишається інертним (ніхто його більше не викликає).
6. **JSONC у `~/.qwen/settings.json`** (коментарі/трейлінг-коми) → `json.loads`
   падає → merge відмовляється, файл **не** переписується, non-zero з
   `install-hooks: qwen: … is not valid JSON`. Recovery — у README-кукбуку
   (прибрати коментарі або тимчасово прибрати файл).
7. **`qwen` на PATH, але `~/.qwen/` немає** → `mkdir -p ~/.qwen` + новий
   `settings.json` з правами 0600 і лише нашими hook-entries.
8. **`~/.qwen/settings.json` існує, а бінарника `qwen` немає** → gate пропускає
   (файл — достатній сигнал), реєструємо.
9. **`~/.qwen/settings.json` існує, але не JSON-об'єкт** (масив/скаляр) →
   та сама помилка, що й для Claude: non-zero, нічого не пишемо.
10. **Обидва pointer-файли** (`CLAUDE.md` і `QWEN.md`) з різними `## Wiki` →
    виграє перший валідний у порядку `CLAUDE.md AGENTS.md GEMINI.md QWEN.md`;
    поведінка детермінована й задокументована в discovery-versioning.
11. **Стала `CLAUDE_PROJECT_DIR` усередині Qwen-сесії** (успадкована з
    середовища) має вищий пріоритет за `QWEN_PROJECT_DIR` → теоретично інший
    anchor. Шкоду обмежують fail-closed-без-git, boundary-guard і version-gate:
    у гіршому разі телеметрія не пишеться, чуже нічого не мутується.
12. **Qwen пише файли через `run_shell_command`** → PostToolUse із файловим
    matcher-ом не спрацьовує, телеметрії немає. Той самий відомий розрив, що й
    із Claude `Bash`; не покривається (див. Поза скоупом).
13. **Matcher-семантика Qwen.** Якщо matcher матчиться підрядком, `edit`
    покриває і `notebook_edit` — union у case робить це нешкідливим у будь-якому
    разі.
14. **Concurrent install + uninstall** на різних клієнтах: кожен settings-файл
    під власним lock-ом, локи не вкладаються → mutual exclusion збережено,
    deadlock неможливий.
15. **`~/.qwen/skills` уже існує як реальний каталог із чужим вмістом** →
    `export_skill_link` поводиться як для gemini (не перезаписує чуже, статус
    `skipped` у summary).
16. **Права наявного settings-файла** (напр. 0644) не звужуються мовчки —
    `st_mode` зберігається при перезаписі. Формально це дельта й для
    Claude-шляху, але лише в бік «не змінювати чуже»; поведінка хуків не
    зачіпається.
17. **`tool_input` з кількома шляховими ключами одночасно** (`file_path` +
    `path` як legacy-дубль, або підкинутий зайвий ключ) → first-match-wins дає
    рівно один бамп; жодних фантомних записів у `.usage.json`. Якщо первинний
    шлях не пройшов boundary-guard / фільтри (`*.md`, не `index|schema|log`),
    хук просто нічого не пише — **fallback на наступний ключ свідомо не
    робиться**: інакше «відхилений первинний + прийнятний вторинний»
    перетворився б на обхід гарда через другий ключ.
18. **Сироти-hook-entries лише в `~/.qwen/settings.json`** (Qwen-only
    користувач; клон скіла зник або `hooks/uninstall-hooks.sh` видалено) →
    orphan-guard `uninstall.sh` бачить маркер у qwen-файлі, ставить
    `HOOKS_FAILED=1` і **не** видаляє `$SKILL_DIR` під `--remove-clones`, тож
    recovery-скрипт лишається доступним. Без цієї правки entries застрягли б
    назавжди, будучи при цьому тихо-інертними через `test -x`-обгортку.

| # | Ризик | Мітигація |
|---|---|---|
| R1 | Схема Qwen hook-envelope зміниться в майбутніх версіях (звірено на qwen-code 0.21.11) | Невалідний envelope у Qwen = «info»-повідомлення, не крах; wrapper завжди `exit 0`; Claude-шлях не зачеплено |
| R2 | Секрети в `~/.qwen/settings.json` (`env`, `modelProviders`) — інсталер читає й переписує файл | Read-under-lock + backup із збереженням прав + atomic replace; жодного друку вмісту; нові файли 0600; наявні права не звужуються |

| R4 | `~/.qwen/skills` як discovery-tier не верифіковано настільки ж, як gemini | Symlink інертний, якщо не використовується; вартість помилки ≈ 0; фактична перевірка — rollout-крок 4 |

| R6 | 5-та колонка Platform-таблиці ламає `skill-contracts.sh` | Асерт правиться в тому ж комміті |
| R7 | Розширення екстрактора stdin (`path`, `notebook_path`) теоретично зачіпає Claude-парсинг | Action-gate по `tool_name` відсікає все поза case ще до резолюції; у Claude-матчерах цих ключів немає; `file_path` завжди виграє first-match-wins; окремий тест «Claude-кейси незмінні» |

## Поза скоупом

- HTTP-хуки, поля `timeout`/`name` в entries, PreToolUse.
- Глобальний `~/.qwen/QWEN.md` (лише проєктні resident-файли).
- Автовидалення інсталером зовнішнього `~/.qwen/hooks/wiki-session-start.sh` —
  свідомо ручний rollout-крок (не видаляємо чужих файлів у чужому каталозі).
- Додавання `NotebookEdit` до **Claude**-матчера PostToolUse (розширило б
  Claude-поверхню — окремий цикл).
- Телеметрія для файлів, записаних через shell (`run_shell_command` / `Bash`).
- Будь-які зміни on-disk схеми вікі, `wiki_version`, міграції.
- Codex-специфічні хуки (Codex і далі покривається текстовим контрактом).

## Done-when (rollout на машині користувача; після посадки, поза движком)

1. `bash hooks/install-hooks.sh` → `~/.qwen/settings.json` вказує на канонічні
   хуки, legacy-entries зникли, чужі ключі на місці.
2. `rm ~/.qwen/hooks/wiki-session-start.sh` (+ порожня `~/.qwen/hooks/`).
3. Live-перевірка в Qwen-сесії на тест-проєкті: індекс інжектнуто; read/edit
   wiki-сторінки → `.usage.json` bump + свіжий `_hooks.post_tool_use_at`.
4. `install.sh --repair-exports` → `~/.qwen/skills/wiki` існує; усі чотири
   тест-сюїти зелені; Claude/Codex/Gemini поведінка незмінна.

## Інваріанти (НЕ ослаблювати)

- DRY: канонічна логіка лишається в `hooks/` + `hooks/lib/`; Qwen-специфіка —
  лише тонкий транспорт-шар і union-переліки.
- Кожен шлях кожного хука завершується `exit 0` і ніколи не блокує інструмент
  чи старт сесії.
- Boundary-guard, fail-closed-без-git і version-gate — без послаблень; хук
  ніколи не пише у вікі поза поточною схемою.
- Claude / Codex / Gemini поведінка незмінна (регрес-нуль).
