Розбіжність номера з текстом — НЕ підстава вважати задачу невиконуваною: `grep -n` по анкеру і працюй далі.

## Спільні інваріанти (НЕ ослаблювати в жодній задачі)

- **Union, а не branch** у логіці хуків. Ніде не з'являється `if qwen … else claude …`. До наявних переліків (tool-names, instruction-файли, env-змінні) **додаються** Qwen-значення; Claude-значення лишаються **першими** й незмінними. **Виняток, зафіксований спекою:** вибір шляху зі stdin — не union, а **first-match-wins** (див. T3).
- **DRY.** Канонічна логіка (discovery, boundary-guard, version-gate, JSON r-m-w, мутекс settings-файла) живе в одному місці. Qwen-специфіка — тонкий транспорт-wrapper і union-переліки. **Другої реалізації мутекса не існує** (T5).
- Кожен шлях кожного хука завершується `exit 0` і НІКОЛИ не блокує інструмент чи старт сесії.
- Boundary-guard, fail-closed-без-git і version-gate — без послаблень.
- **Один tool call однофайлового інструмента → рівно ОДИН бамп** у `.usage.json`. Кілька шляхів за виклик дозволені лише `BATCH_TOOLS` (`{"MultiEdit"}`), і `BATCH_TOOLS ⊂ action-gate`.
- **Перевірка hook-маркера й видалення `$SKILL_DIR` — в одному критичному відрізку** під тими самими lock-ами, що бере інсталер; неможливість перевірити = НЕ видаляти. Межа інваріанта фіксується явно: мутекс упорядковує критичні відрізки, але не скасовує запис, що стартував ПІСЛЯ звільнення локів. Інсталер, який чекав на лок і отримав його вже після видалення `$SKILL_DIR`, штатно допише свої entries; такі entries інертні за конструкцією обгортки (`test -x "…" && "…" || exit 0`) і прибираються наступним `uninstall-hooks.sh`. Заборонено саме видалення клону при живих entries — а не поява інертних entries після завершення uninstall-у.
- **Глобальний порядок взяття settings-локів — `claude` → `qwen`**, однаковий для всіх, хто тримає два одночасно (`uninstall-hooks.sh` T8, orphan-guard T12). Інсталер тримає рівно один лок за раз і ніколи не чекає на другий, утримуючи перший. Циклу очікувань не існує ⇒ deadlock неможливий за конструкцією, а не за таймінгом.
- **Жодного блокуючого читання по не-звичайному файлу.** Перед будь-яким `grep`/відкриттям settings-шляху перевіряється `-f`; не-звичайний шлях (FIFO, сокет, каталог, пристрій, битий симлінк) НЕ читається взагалі й трактується як «перевірити неможливо» (fail-closed). Саме читання додатково обмежене дедлайном — інакше один `mkfifo` на місці settings-файла вішає скрипт назавжди, а під локами — ще й нікому їх не віддає.
- `python3` — ЛИШЕ для JSON read-modify-write; відсутній `python3` → тихий `exit 0` у хуках (в інсталерах — наявний контракт кодів виходу).
- Жоден вміст settings-файлів (у т.ч. секрети) не друкується в stdout/stderr.
- Claude / Codex / Gemini поведінка незмінна (регрес-нуль). Наявні тести — регрес-детектор; **жоден наявний assert не послаблюється й не видаляється**, лише додаються нові. Планом дозволено рівно **два** точкові перенацілювання наявних статичних assert-ів, обидва — в тому ж комміті, що змінює перевіряний рядок, і обидва — без послаблення перевірки: сепаратор Platform-таблиці (T13) і статичний assert взяття мутекса `tests/hooks/run.sh:1790` (T5). Інших правок наявних assert-ів немає.
- `wiki_version` = `"4.0"`. Нуль міграцій, нуль backfill, нуль змін on-disk схеми.

**Канонічний id: `t3-ptu-first-match`** — стабільний ідентифікатор задачі у графі (knownDone, stop-loss-лічильники і done-піни деривуються з нього; НЕ перечеканювати).

### Що зробити

Правки **лише всередині python-екстрактора** `hooks/post-tool-use.sh:268-307`.

1. **Скалярні ключі — first-match-wins, НЕ union.** Замість одного `add(tool_input.get("file_path", ""))` (`:298`):
   ```python
   # Exactly ONE primary path per tool call: the first non-empty string in
   # this chain wins and the remaining keys are NOT read (spec R9). All
   # matched Qwen tools (read_file/write_file/edit/notebook_edit) are
   # single-file, so a union here would bump several .usage.json records for
   # one call — silently inflating telemetry via a legacy duplicate `path`
   # or an injected extra key.
   for _key in ("file_path", "notebook_path", "path"):
       _v = tool_input.get(_key, "")
       if isinstance(_v, str) and _v:
           add(_v)
           break
   ```
   Для matched Claude-інструментів `file_path` присутній завжди, тож ланцюжок зупиняється на першій ланці й `notebook_path`/`path` для них не читаються ніколи.
2. **`edits[]` — адитивний union ЛИШЕ для batch-імен.** Наявний цикл `:300-304` загортається в перевірку окремого переліку, що живе **в самому екстракторі** (поряд зі скалярним ланцюжком, де `tool_name` уже розпарсений):
   ```python
   # BATCH_TOOLS ⊂ the bash action-gate `case "$tool_name"` in main(). The
   # action-gate decides "do we count this call at all"; BATCH_TOOLS decides
   # "may this call yield more than one path". A future batch tool = one
   # edit in BOTH places, same commit.
   BATCH_TOOLS = {"MultiEdit"}
   if tool_name in BATCH_TOOLS:
   ```

## Task 8 — `hooks/uninstall-hooks.sh`: параметризація + qwen + legacy-маркер

**Канонічний id: `t8-uninstall-hooks`** — стабільний ідентифікатор задачі у графі (knownDone, stop-loss-лічильники і done-піни деривуються з нього; НЕ перечеканювати).

**Хвиля 8.** Залежить від T5 і T7. Диф ~170 рядків коду + ~150 рядків тестів.

### Що зробити

1. **Дві фази — але в ОДНОМУ python-процесі (вердикт s5, ⛔ не розщеплювати на окремі виклики).** Замість монолітного `strip_from <client> <settings_file>` і замість чотирьох окремих викликів (`plan`×2, `commit`×2) — рівно один `python3` під уже взятими локами, який отримує обидва шляхи в argv і всередині себе проходить дві фази:
   - **фаза plan (для кожного клієнта):** `os.open(O_RDONLY|O_NOFOLLOW|O_NONBLOCK)` → `fstat`/`S_ISREG` (п.5) → read → валідація (`json.load`, перевірка «це об'єкт») → merge. **Оригінальні байти й обчислений результат лишаються В ПАМ'ЯТІ процесу**; на диск у цій фазі не пишеться нічого, цільові файли не чіпаються. Стан клієнта: `nochange` / `planned` / `error`;
   - **фаза commit (лише коли ОБИДВА клієнти не в `error`):** для кожного `planned` — `mkstemp` у теці цільового файла → `fchmod` під `st_mode` джерела → запис → `os.close` → backup через `os.open(O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW)` у `"$settings_file.bak-wiki-hooks-$TS"` (нумерований суфікс при колізії) із **байтів у пам'яті**, а не `shutil.copy2` з диска → `os.replace(tmp, settings_file)`.
   Чому один процес: доки фази були окремими викликами, tmp лежав на диску всю фазу планування ДРУГОГО клієнта — вікно на кілька порядків довше за необхідне, і саме воно давало підставу знахідкам рану №4. Тепер tmp існує мілісекунди всередині процесу, який його створив.
2. **Один критичний відрізок на обох клієнтів**, що тримає **обидва** локи в глобальному порядку `claude` → `qwen` (той самий порядок, що в T12; звільнення — у зворотному, `qwen` → `claude`). Локи бере й віддає bash (п.9/п.10), усе інше робить той самий один python-виклик. Порядок усередині нього строго такий:
   `plan(claude)` → `plan(qwen)` → [будь-який `error` ⇒ вихід non-zero, нічого не записано] → `commit(claude)` → `commit(qwen)`.
   Чому не «повний протокол по клієнту послідовно», як в інсталері: тоді corrupt JSON у qwen виявляється вже ПІСЛЯ `os.replace` claude-файла, і uninstall лишає систему в напівзнятому стані. Тут же валідація обох файлів завершується до першого запису, тож «corrupt Qwen JSON ⇒ жоден settings-файл не змінено» — властивість конструкції, а не везіння.
2а. **Прибирання артефактів розрізняє tmp і backup (вердикт s7).** Аварійне/сигнальне прибирання (список in-flight файлів, `trap`, гілки помилок) зачищає **лише tmp**. Backup `.bak-wiki-hooks-*` до цього списку НЕ потрапляє ніколи і не видаляється на жодному шляху виходу: це recovery-копія для людини, а не тимчасовий файл, і v4.5 її теж лишає на диску (у `master` немає жодного видалення по цьому шляху). Інакше сигнал, що прилетів одразу після вдалого `os.replace`, зносить ЄДИНУ копію вже зміненого файлу — саме цей P1 завалив хвилю рану №5.
3. **Ніякого запису, поки не спланована зміна для обох клієнтів.** Будь-яка невдача фази plan (corrupt JSON, JSONC-коментарі, не-об'єкт, не-звичайний шлях, відсутній `python3` за наявного маркера, помилка I/O) → non-zero, **жоден** із двох файлів не переписано і **жодного `.bak-wiki-hooks-*` не створено** (backup живе у фазі commit, безпосередньо перед `os.replace`). Tmp-файли фази plan видаляються на всіх шляхах виходу.
4. **Rollback другої фази — рівно для ЗВИЧАЙНИХ відмов, не для сигналів, і З ПАМ'ЯТІ, не з backup-файла (вердикт s5).** `commit(claude)` успішний, `commit(qwen)` впав (ENOSPC, I/O) → claude негайно відновлюється: **оригінальні байти, які фаза plan лишила в пам'яті цього ж процесу**, пишуться у свіжий `mkstemp` і кладуться на місце тим самим `os.replace`. Backup-файл при цьому НЕ читається взагалі — він артефакт для людини, а не джерело істини, тож підміна його шляху нічого не публікує. Якщо і rollback не вдався — окреме повідомлення з **абсолютним шляхом** backup-а й інструкцією відновити вручну. `os.replace` у межах однієї теки атомарний, тож проміжного «половинчастого» файла не існує в жодній із гілок. **Сигнал (INT/TERM), що прилетів у вікні між двома commit-ами, автоматичного відкату НЕ запускає** (вердикт s4): trap лише прибирає tmp і локи, віддає ЧЕСНИЙ ненульовий код (`exit 130`/`exit 143` перед EXIT-гілкою — читання stale `$?` заборонено, бо `uninstall.sh` трактує `exit 0` як дозвіл видалити клон відновлення) і друкує «повторіть `hooks/uninstall-hooks.sh`». Напівзнятий стан у цьому вікні — задекларований residual, а не дефект: uninstall ідемпотентний, повторний запуск його сходить.
5. **Не-звичайний settings-шлях** (FIFO, сокет, каталог, пристрій, битий симлінк) → для цього клієнта операція неможлива: `error` (non-zero), нічого не записано. Fail-closed, бо видалення entries не можна ні виконати, ні верифікувати. **Механіка — НЕ `-f`-передперевірка, а той самий гард відкриття, що в T6 п.9** (TOCTOU: підміна на FIFO між `-f` і `open()` підвішує процес назавжди, у цій задачі — під обома локами): `os.open(path, os.O_RDONLY | getattr(os, "O_NOFOLLOW", 0) | getattr(os, "O_NONBLOCK", 0))` → `os.fstat` → `stat.S_ISREG`, не-regular → `error`. `ENOENT` — штатний `nochange` (п.7).

Порядок від цього не змінюється: беруться ті з двох локів, що потрібні, у тому самому порядку `claude` → `qwen`.

13. **⛔ Скоуп-пін і модель загроз (вердикти s3/s4 — рішення контролера після рану №3, НЕ переглядати в рев'ю).** Механізм задачі — рівно пункти 1–12 вище. У ньому НЕ з'являються: sha256-звірки вмісту (`pre_digest`/`post_digest`, «примирення плану з диском»), верифікація `dev`/`ino` tmp-файла перед `os.replace`, повторне взяття локів заради клієнта, чия тека виникла посеред рану, і сигнальний EXIT-trap rollback. Підстава: settings-файли живуть у per-user `$HOME` (`~/.claude`, `~/.qwen`) — хто здатен підмінити наш tmp чи backup, той уже має право переписати і самі хуки, і клон скіла, тож звірка вмісту нічого не додає до моделі загроз; конкурентні **процеси** впорядковує mkdir-мутекс T5, а не digest. Історія, що зробила пін необхідним: два фікс-раунди хвилі 4 наростили саме ці механізми (`c09ac5f`, `8ff4713`), і наступний раунд рев'ю видав 6 P1 — усі шість у коді, доданому цими фіксами; ліміт раундів вичерпався на ескалації `indivisible`. **Задекларовані residual (їх закривати НЕ треба — треба назвати в коментарі коду):** (а) сигнал між двома `os.replace` лишає напівзнятий стан → чесний non-zero + порада повторити (п.4); (б) сторонній запис у settings-файл між `plan` і `commit` буде перезаписаний спланованим вмістом — та сама семантика, що в наявному інсталері v4.5; (в) поява теки клієнта після взяття локів — пост-локова гонка, легальна за тим самим міркуванням, що T12 п.6; (г) **вікно між `os.close(tmp)` і `os.replace(tmp, …)` у межах одного процесу** — `rename(2)` у Python адресує ШЛЯХ, `renameat2`/`RENAME_NOREPLACE` недоступний, тож перевірка перед `replace` вікна не закриває, а лише зсуває (вердикт s6; рев'юери циклу вже дали P1 обом крайнощам — «перевірки нема» і «перевірка є, але fd закрито до replace»). Ланцюг гарантій закінчується тут: непередбачуване `mkstemp`-ім'я, per-user тека, ідемпотентний повторний запуск.

   ```bash

   scan_marker() {
     local f="$1" gpid wpid rc=0

     kill -TERM "$wpid" 2>/dev/null || true
   ```

   - **Дедлайн-вартовий — другий рубіж**, а не дублювання: він закриває залишковий TOCTOU (шлях підмінили на FIFO між `-f` і `open`) і зависання на збійному/мережевому FS.
