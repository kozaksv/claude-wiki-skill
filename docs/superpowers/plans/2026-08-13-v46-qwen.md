## Worktree discipline (читати ПЕРЕД будь-якою задачею)

- Це **окремий worktree**; твій shell cwd може бути ІНШИМ worktree. НІКОЛИ голий `git`.
- Усі git: `git -C "/Users/a/AI/claude-wiki-skill/.claude/worktrees/v46-qwen" …`.
- Усі Read/Edit/Write і файлові Bash — ЛИШЕ за АБСОЛЮТНИМИ шляхами під коренем вище.
- Будь-який run/тест: `cd "/Users/a/AI/claude-wiki-skill/.claude/worktrees/v46-qwen" && …`.
- Перед КОЖНИМ комітом: `git -C "…root…" status --short` МАЄ показувати САМЕ твої файли. Порожньо / не ті → писав не туди, виправ абсолютний шлях ПЕРШ ніж комітити.
- Коміть лише файли своєї задачі явними абсолютними шляхами.
- **Симлінк-пастка:** `~/.claude/skills/wiki` — симлінк на ОСНОВНИЙ репо, не на цей worktree. Ніколи не тестуй проти `~/.claude/...` чи `~/.qwen/...` — ЛИШЕ проти tmp-фікстур із підміненим `HOME`.

## Спільні інваріанти (НЕ ослаблювати в жодній задачі)

- **Union, а не branch.** Ніде не з'являється `if qwen … else claude …`. До наявних переліків (tool-names, stdin-ключі, instruction-файли, env-змінні) **додаються** Qwen-значення; Claude-значення лишаються **першими** й незмінними.
- **DRY.** Уся канонічна логіка (discovery, boundary-guard, version-gate, JSON r-m-w) лишається там, де вона є. Qwen-специфіка — рівно два місця: тонкий транспорт-wrapper і union-переліки.
- Кожен шлях кожного хука завершується `exit 0` і НІКОЛИ не блокує інструмент чи старт сесії.
- Boundary-guard, fail-closed-без-git і version-gate — без послаблень.
- `python3` — ЛИШЕ для JSON read-modify-write; відсутній `python3` → тихий `exit 0` у хуках (в інсталерах — наявний контракт кодів виходу).
- Claude / Codex / Gemini поведінка незмінна (регрес-нуль). Наявні тести — регрес-детектор; **жоден наявний assert не послаблюється**, лише додаються нові (єдині винятки — три статичні assert-и, явно названі в задачах 4 і 9).
- `wiki_version` = `"4.0"`. Нуль міграцій, нуль backfill, нуль змін on-disk схеми.
- Жоден вміст settings-файлів (у т.ч. секрети) не друкується в stdout/stderr.

## Task 3 — `hooks/session-start-qwen.sh` (новий транспорт-wrapper)

**Хвиля 3.** Диф ~45 рядків нового файла + ~60 рядків тестів + 3 рядки guard-ів.

### Що зробити

Створити **NEW** `hooks/session-start-qwen.sh` (chmod +x; переконатись, що git записує mode `100755`):

1. `set -uo pipefail`; `HOOK_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"`.
2. Викликати **сусідній канонічний** `"$HOOK_DIR/session-start.sh"` — **НІКОЛИ** hardcoded `$HOME/...`. Захопити його **stdout** у змінну; stderr дочірнього хука **не** перенаправляти в stdout (діагностика лишається в stderr wrapper-а — Qwen її не парсить).
3. Порожній stdout (нема вікі / discovery не резолвнув / хук вирішив мовчати) → **нічого не друкує** і `exit 0`. Порожній envelope створив би шумове «info»-повідомлення в КОЖНІЙ сесії без вікі (spec edge 1).
4. Немає `python3` (`command -v python3` фейлить) → тихий `exit 0` без друку (spec edge 2). Перевірка робиться **до** пакування; чи до виклику дочірнього хука — на розсуд виконавця, але тоді дочірній хук теж не запускається, що дешевше й теж коректно (він сам без python3 лише пропускає heartbeat).
5. Непорожній stdout → `python3` пакує його `json.dumps` в ОДИН рядок stdout:
   ```json
   {"continue":true,"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}
   ```
   Текст передавати в python через **stdin** (`printf '%s' "$out" | python3 -c …`), не через argv — уникає лімітів argv і проблем екранування. Дочірній хук stdin не читає, тому підміна stdin для python безпечна (spec edge 3).
6. Кожен шлях завершується `exit 0`; wrapper НІКОЛИ не блокує старт сесії. Помилка `python3` (ненульовий код) → теж `exit 0` без друку.

8. **`hooks/session-start.sh` НЕ ЗМІНЮЄТЬСЯ ВЗАГАЛІ.** Claude-шлях недоторканий: 24 KB cap, untrusted-data преамбула, lint-reminder, `_hooks` heartbeat — усе успадковується як є.

## Task 4 — `hooks/install-hooks.sh`: параметризація `register_into` (claude-only, поведінка та сама) + збереження прав

**Хвиля 4.** Найтонше місце репо (spec R5) — робиться ОКРЕМО від додавання qwen, щоб наявні lock-тести працювали як чистий регрес-детектор. Диф ~170 рядків.

### Що зробити

1. Винести тіло «register into settings-file» у функцію **`register_into <settings_file> <client>`**, що виконує ТОЙ САМИЙ протокол, що зараз: mkdir-lockdir мутекс → read-under-lock → timestamped backup → python3-merge по маркеру → atomic tmp + `os.replace`.
2. **Стан lock-у стає per-call.** `LOCK_DIR` і `LOCK_ACQUIRED_MKDIR` (`:75`, `:92`) виставляються на початку кожного виклику; `on_exit`-trap (`:94-116`) працює з **поточним** `LOCK_DIR`. Після кожного виклику lock звільняється **явно** (функція `release_lock`: якщо `LOCK_ACQUIRED_MKDIR=1` і `cat "$LOCK_DIR/pid"` = `$$` → `rm -f pid; rmdir`; далі `LOCK_ACQUIRED_MKDIR=0`), **не лише в trap-і**.
3. **Локи беруться послідовно, НІКОЛИ не вкладено** (готує ґрунт для T5; deadlock неможливий — spec edge 14).
4. `fail()` (`:61-64`) отримує префікс клієнта: `install-hooks: <client>: …`. Той самий префікс передається в python-merge аргументом і використовується в УСІХ його `sys.stderr.write` (`:260`, `:268`, `:273`, `:279`, `:286`).
5. **Права результуючого файла (spec edge 16, R2):** у python-merge — якщо `settings_file` існував, зчитати його `st_mode` ДО запису й застосувати `os.chmod(tmp_path, mode)` перед `os.replace`; якщо файл створюється з нуля — `0600`. Причина: `mkstemp` дає 0600 і `os.replace` мовчки звузив би права наявного файла. Формально це дельта й для Claude-шляху, але лише в бік «не змінювати чуже».
