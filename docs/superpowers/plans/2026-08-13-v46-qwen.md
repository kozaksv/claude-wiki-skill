## Worktree discipline (читати ПЕРЕД будь-якою задачею)

- Це **окремий worktree**; твій shell cwd може бути ІНШИМ worktree. НІКОЛИ голий `git`.
- Усі git: `git -C "/Users/a/AI/claude-wiki-skill/.claude/worktrees/v46-qwen" …`.
- Усі Read/Edit/Write і файлові Bash — ЛИШЕ за АБСОЛЮТНИМИ шляхами під коренем вище.
- Будь-який run/тест: `cd "/Users/a/AI/claude-wiki-skill/.claude/worktrees/v46-qwen" && …`.
- Перед КОЖНИМ комітом: `git -C "…root…" status --short` МАЄ показувати САМЕ твої файли. Порожньо / не ті → писав не туди, виправ абсолютний шлях ПЕРШ ніж комітити.
- Коміть лише файли своєї задачі явними абсолютними шляхами.
- **Симлінк-пастка:** `~/.claude/skills/wiki` — симлінк на ОСНОВНИЙ репо, не на цей worktree. Ніколи не тестуй проти реальних `~/.claude/…` чи `~/.qwen/…` — ЛИШЕ проти tmp-фікстур із підміненим `HOME`.

## Спільні інваріанти (НЕ ослаблювати в жодній задачі)

- **Union, а не branch** у логіці хуків. Ніде не з'являється `if qwen … else claude …`. До наявних переліків (tool-names, instruction-файли, env-змінні) **додаються** Qwen-значення; Claude-значення лишаються **першими** й незмінними. **Виняток, зафіксований спекою:** вибір шляху зі stdin — не union, а **first-match-wins** (див. T3).
- **DRY.** Канонічна логіка (discovery, boundary-guard, version-gate, JSON r-m-w, мутекс settings-файла) живе в одному місці. Qwen-специфіка — тонкий транспорт-wrapper і union-переліки. **Другої реалізації мутекса не існує** (T5).
- Кожен шлях кожного хука завершується `exit 0` і НІКОЛИ не блокує інструмент чи старт сесії.
- Boundary-guard, fail-closed-без-git і version-gate — без послаблень.
- **Один tool call однофайлового інструмента → рівно ОДИН бамп** у `.usage.json`. Кілька шляхів за виклик дозволені лише `BATCH_TOOLS` (`{"MultiEdit"}`), і `BATCH_TOOLS ⊂ action-gate`.
- **Перевірка hook-маркера й видалення `$SKILL_DIR` — в одному критичному відрізку** під тими самими lock-ами, що бере інсталер; неможливість перевірити = НЕ видаляти.
- `python3` — ЛИШЕ для JSON read-modify-write; відсутній `python3` → тихий `exit 0` у хуках (в інсталерах — наявний контракт кодів виходу).
- Жоден вміст settings-файлів (у т.ч. секрети) не друкується в stdout/stderr.
- Claude / Codex / Gemini поведінка незмінна (регрес-нуль). Наявні тести — регрес-детектор; **жоден наявний assert не послаблюється й не видаляється**, лише додаються нові (єдиний виняток — статичний assert сепаратора Platform-таблиці, явно названий у T13).

## Task 3 — `hooks/post-tool-use.sh`: first-match-wins + `BATCH_TOOLS` (spec R9)

**Хвиля 3.** Залежить від T2 (action-gate вже стоїть першим — на цьому тримаються гарди `Grep`/`Glob`). Диф ~25 рядків коду + ~130 рядків тестів.

### Що зробити

Правки **лише всередині python-екстрактора** `hooks/post-tool-use.sh:268-307`.

1. **Скалярні ключі — first-match-wins, НЕ union.** Замість одного `add(tool_input.get("file_path", ""))` (`:298`):
   ```python
   # Exactly ONE primary path per tool call: the first non-empty string in
   # this chain wins and the remaining keys are NOT read (spec R9). All
   # matched Qwen tools (read_file/write_file/edit/notebook_edit) are
   # single-file, so a union here would bump several .usage.json records for
   # one call — silently inflating telemetry via a legacy duplicate `path`
   # or an injected extra key.
   for _key in ("file_path", "notebook_path", "path"):
       _v = tool_input.get(_key, "")
       if isinstance(_v, str) and _v:
           add(_v)
           break
   ```
   Для matched Claude-інструментів `file_path` присутній завжди, тож ланцюжок зупиняється на першій ланці й `notebook_path`/`path` для них не читаються ніколи.
2. **`edits[]` — адитивний union ЛИШЕ для batch-імен.** Наявний цикл `:300-304` загортається в перевірку окремого переліку, що живе **в самому екстракторі** (поряд зі скалярним ланцюжком, де `tool_name` уже розпарсений):
   ```python
   # BATCH_TOOLS ⊂ the bash action-gate `case "$tool_name"` in main(). The
   # action-gate decides "do we count this call at all"; BATCH_TOOLS decides
   # "may this call yield more than one path". A future batch tool = one
   # edit in BOTH places, same commit.
   BATCH_TOOLS = {"MultiEdit"}
   if tool_name in BATCH_TOOLS:
       edits = tool_input.get("edits", [])
       if isinstance(edits, list):
           for item in edits:
               if isinstance(item, dict):
                   add(item.get("file_path", ""))
   ```
   Для всіх інших дозволених імен ключ `edits` **не читається взагалі**, навіть якщо він присутній у payload.
3. Порядок-стабільний dedup через `seen` і адитивність поверх первинного шляху для `MultiEdit` не змінюються (там кілька бампів за виклик коректні).
4. Оновити header-коментар `:28-37` («MultiEdit shape»): описати два різні режими — first-match-wins для скалярів і batch-only union для `edits[]`, з фіксованим інваріантом `BATCH_TOOLS ⊂ action-gate` і посиланням на дві незалежні причини нульового впливу на Claude (зареєстрований matcher `Read|Edit|Write|MultiEdit` + action-gate). **Не** писати обґрунтування «цих ключів у Claude немає» — воно хибне (`Glob`/`Grep` мають `path`).
5. Явно **не** робити fallback на наступний ключ, якщо первинний шлях не пройшов boundary-guard/фільтри (spec edge 17): інакше «відхилений первинний + прийнятний вторинний» став би обходом гарда через другий ключ.

**Хвиля 12.** Залежить від T5 (`settings-lock.sh`) і T11 (перелік файлів). Диф ~90 рядків коду + ~140 рядків тестів. Закриває TOCTOU: між `grep` і видаленням `$SKILL_DIR` лежать зняття експортів і `rmdir`.

### Що зробити

1. **Сорснути lib поряд із собою:**
   ```bash
   SELF_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
   LOCK_LIB="$SELF_DIR/hooks/lib/settings-lock.sh"
   ```
   Lib недоступний (скрипт запущено відірвано від клону) → **locked-recheck неможливий** → консервативний skip видалення `$SKILL_DIR` з явним поясненням (`HOOKS_FAILED=1`).

   1. (поза локами, там де зараз, `:122-140`) виклик `hooks/uninstall-hooks.sh` для верифікованого клону; запам'ятати факт запуску (`UNINSTALLER_RAN=1`) і його результат. **Виклик лишається ПОЗА відрізком** — він бере ті самі локи всередині себе, тож вкладення дало б гарантований self-deadlock;
   2. (поза локами) зняття експортів + `rmdir` (`:144-153`);
   3. **критичний відрізок** (обидва локи, фіксований глобальний порядок **claude → qwen**):
      - recheck маркера в обох файлах (логіка T11);
      - друк попередження + `HOOKS_FAILED=1`, якщо маркер лишився. Якщо `UNINSTALLER_RAN=0` — **наявний** текст із `записи hooks лишились`; якщо `UNINSTALLER_RAN=1` і маркер усе одно лишився — окремий текст про залишки, теж із `HOOKS_FAILED=1`;
      - рішення щодо `$SKILL_DIR` під `--remove-clones`: skip (наявний рядок із `git hooks removal failed`) або `remove_clone_dir "$SKILL_DIR"`;
      - звільнення у зворотному порядку qwen → claude;
   4. (поза локами) `remove_clone_dir "$DOC_EXTRACT_DIR"`, підсумок.
   **Відрізок виконується в ОБОХ режимах:** без `--remove-clones` він лише друкує попередження й одразу віддає локи. Формат виводу (`echo ""`, `Real clone directories:` тощо) зберегти.
3. **Невдача взяття будь-якого з двох локів за `LOCK_TIMEOUT`** → поводимось як за наявного маркера: `HOOKS_FAILED=1`, `$SKILL_DIR` **не** видаляється, друкуються причина й команда для повторного запуску. «Не змогли перевірити» ніколи не читається як «нема чого захищати». Якщо взято перший лок, а другий не вдався — **перший звільнити** перед виходом із відрізка.
4. **Deadlock неможливий за конструкцією:** інсталери беруть локи послідовно й ніколи не тримають один, чекаючи другого; єдиний власник обох одночасно — цей відрізок, і він бере їх у канонічному порядку. Зафіксувати це коментарем поряд із взяттям.
